# 项目优化与功能建议报告

## 1. 评估范围
- 评估对象：启动器、GUI、视频模式、有题目模式、纯答题模式、配置与工程文件。
- 评估目标：按功能识别现有问题与可优化点，并给出建议新增功能。

## 2. 按功能的现有问题与优化建议

### 2.1 启动与配置管理
**现有问题**
- GUI 中“多实例运行”只有界面变量，没有被运行逻辑使用，属于未落地功能。
- GUI 的 `log_queue` 只定义和消费，没有实际生产端写入，结构冗余。
- GUI 配置校验强制要求 `course_name`，与“可只填 `course_url`”的能力不一致。
- 文档中提到“启动图形化界面.bat”，但根目录启动脚本文件名为 `start_gui.bat`，文档与实现不一致。

**可优化点**
- 将“多实例运行”映射为实际行为：多进程启动、互斥检查、端口/日志隔离。
- 删除无用队列或统一走队列架构（主线程 UI 渲染，后台线程只投递消息）。
- 配置校验改为“`course_name` 与 `course_url` 二选一必填”。
- 统一文档和脚本命名，避免新用户按文档无法启动。

### 2.2 模式路由（智能启动器）
**现有问题**
- 模式分发依赖 `mode + course_type` 组合，兼容逻辑较多，后续新增模式时容易分支膨胀。

**可优化点**
- 将模式映射抽象为注册表（mode -> handler），把兼容转换逻辑前置为单独函数，减少主流程分支复杂度。

### 2.3 视频自动播放（无题目模式）
**现有问题**
- 文件体量大、职责重（登录、找课、播放、异常恢复、反检测、进度统计耦合在同一类）。
- 存在大量通配异常捕获，部分分支会吞掉真实错误，影响定位效率。
- 等待策略中硬等待和随机等待较多，可维护性和稳定性依赖经验值。

**可优化点**
- 进行模块化拆分：认证、课程导航、播放器控制、异常恢复、进度存储。
- 建立异常分层：可恢复异常、需重试异常、致命异常，配套统一错误码。
- 引入统一“等待策略层”（显式条件等待 + 限量随机扰动），降低魔法数分散。

### 2.4 有题目视频模式
**现有问题**
- 同一类中存在重复方法定义（`check_for_quiz`、`answer_quiz` 各有两套实现），后定义会覆盖前定义，导致行为不透明。
- 引入监控线程并在后台线程中直接驱动 WebDriver 操作，存在线程安全风险（Selenium 典型建议为单线程驱动）。

**可优化点**
- 删除重复实现，保留单一权威路径，并为关键方法补充行为测试。
- 改为“主线程轮询 + 事件状态机”处理题目弹窗，避免后台线程直接操作 driver。

### 2.5 纯答题模式（AI 调用）
**现有问题**
- 环境变量命名仍沿用 `ANTHROPIC_*`，但业务已经转为 DeepSeek，语义不一致、易误配。
- 启动即进行 API 连通性问答验证，会增加一次启动耗时和 token 成本。

**可优化点**
- 增加 `DEEPSEEK_*` 变量优先级并保留旧变量兼容读取。
- API 健康检查改为可配置（启动校验开关），默认仅在首次失败或用户主动触发时执行。

### 2.6 工程与交付质量
**现有问题**
- `LICENSE` 文件存在明显冲突标记，属于仓库质量问题。
- 根目录 `README.md` 内容过于简略，不足以承载使用、架构、排障信息。
- `.gitignore` 含根目录 `/*.py`、`/*.bat`、`/*.json` 全局忽略策略，后续新增根目录脚本容易被误忽略。
- 缺少自动化测试与基本 CI 质量门禁（lint/type-check/test）。

**可优化点**
- 先清理冲突文件并建立合并检查。
- 重新组织 README：快速开始、配置模板、模式说明、FAQ、故障排查。
- 调整 `.gitignore` 规则为“精确忽略”，避免误伤。
- 建立最小 CI：静态检查 + 冒烟测试（启动参数、配置解析、模式分发）。

## 3. 建议新增功能（报告增补）

### 3.1 配置健康检查器（高优先级）
- 启动前校验账号、课程定位、模式组合、API 配置、依赖版本。
- 生成“可执行性报告”，提前暴露失败点。

### 3.2 选择器热更新机制（高优先级）
- 将关键 XPath/CSS 提取为外部配置，支持在线更新或版本化回退。
- 平台页面变更时无需改代码即可快速修复。

### 3.3 任务编排中心（中高优先级）
- 支持多账号任务队列、时段调度、并发上限、失败重试策略。
- 统一管理批量任务，避免手工多开脚本。

### 3.4 运行可观测面板（中优先级）
- 显示当前模式、进度、错误分类、重试次数、题目处理结果、API调用统计。
- 方便排障与性能回溯。

### 3.5 失败快照中心（中优先级）
- 统一保存失败时截图、页面 HTML、核心日志片段和上下文参数。
- 形成可回放证据链，减少“无法复现”问题。

### 3.6 安全暂停/恢复（中优先级）
- 提供安全停机点（当前题目/当前视频片段结束后暂停），并支持恢复执行。
- 适配长时间任务的中断与继续需求。

## 4. 建议实施顺序
1. 先修复工程阻断项：`LICENSE` 冲突、重复方法、线程驱动风险。
2. 再做稳定性：配置健康检查、等待策略统一、异常分层。
3. 最后做效率提升：任务编排、可观测面板、选择器热更新。

## 5. 结论
- 当前项目已具备较强的业务能力，但在工程可维护性与稳定性治理方面仍有明显提升空间。
- 若按本报告顺序推进，能显著降低因页面变化、配置不一致、并发运行导致的故障率，并提升长期迭代效率。
